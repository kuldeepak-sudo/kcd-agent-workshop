Open source agents on Kubernetes — MCP server, Tyk OSS Gateway, Tyk AI Studio, and a custom gRPC plugin for identity governance — with governance made visible, not theoretical. Tyk OSS only, no Dashboard, no Enterprise licence.

01 · Architecture

What you're building

Three governance stories, all fronted by open source Tyk components. The agent never talks to the LLM, the MCP server, or a customer-data API directly — every call is intercepted by an open source Tyk component that can authenticate it, rate-limit it, filter what it's allowed to see, narrow its identity, and log it.

LayerComponentWhat it governsLicense
Tool calls (MCP) Tyk OSS Gateway — MCP Gateway feature Auth, per-agent/per-tool rate limits & quotas, filtered tool discovery, structured access logs Fully in the OSS gateway (MPL)
Model calls (LLM) Tyk AI Studio — Community Edition Auth, rate limiting, cost/usage tracking, RBAC on who can call which model Open source (CE)
Identity (Part 2) Custom Tyk OSS gRPC plugin Narrows an inbound token's scope to one action while preserving the caller's identity — RFC 8693-style, without the Enterprise licence that feature normally needs Fully OSS (hand-rolled on the OSS "rich plugins" feature)

Full audit-log persistence and budget enforcement on the AI Studio side are Enterprise-only — say so on stage rather than promising it, and lean on the MCP Gateway's access logs for the audit-trail beat instead.

02 · Before you go on stage

Pre-flight checklist

A live install of four-plus components from a cold cluster eats your whole slot. Do the heavy lifting ahead of time — the live portion re-runs the fast, visible parts and spends its time on the governance payoff. Everything below is scripted now; nothing here needs a manual Helm value hunt.

Tooling on your laptop

  • Docker Desktop (or equivalent) with at least 6 GB RAM allocated
  • kind or k3d — this guide uses kind
  • kubectl, helm 3+, Python 3.10+ — no jq, no Go needed to just run this
  • An API key for one LLM provider (OpenAI or Anthropic) — optional; no key? Skip to the Ollama fallback

Pick your rate-limit numbers ahead of time

Decide now what "trip the rate limit live" looks like — e.g. 5 requests/minute on one tool — so you're not doing arithmetic on stage. See the segment 4 callout: in this build's live testing, the rate limit did not actually trip — verify against your own gateway build before relying on this beat.

Checkpoint: both setup scripts run clean, verify.sh prints all PASS, AI Studio's admin console is reachable, one working LLM API key in hand (if you're attempting segment 3 live). Everything below can now run live in the allotted time.

  • Every framework reinvents its own auth, rate limiting, and logging — or skips it.

Talking point: the (deliberately unguarded) MCP server

curl it from inside the cluster and show it just answers — no API key, no rate limit, no audit trail. That gap is exactly what the governed proxy closes.

The governed MCP proxy — what actually got registered

Tyk models every remote MCP server as a Tyk OAS API definition. Verified against tyk-mock-mcp-server's real tool list and the current schema — the tool allowlist lives at middleware.mcpTools.{toolName}.allow.enabled (per tool, not a single array). The server actually exposes 15 tools (get_users, create_user, update_user, delete_user, get_posts, create_post, get_products, process_order, get_analytics, generate_report, validate_email, generate_uuid, format_date, get_anything, slow_response) — there is no list_users or get_user.

{
  "openapi": "3.0.3",
  "info": { "title": "mock-mcp", "version": "1.0.0" },
  "paths": { "/mcp": { "post": { "responses": {"200": {"description": "ok"}} }, "get": { "responses": {"200": {"description": "ok"}} } } },
  "x-tyk-api-gateway": {
    "info": { "name": "mock-mcp-governed", "state": { "active": true } },
    "server": {
      "listenPath": { "value": "/mcp-gw/", "strip": true },
      "authentication": { "enabled": true, "authToken": { "enabled": true } }
    },
    "upstream": { "url": "http://mock-mcp-server.tyk-oss.svc.cluster.local:7878" },
    "middleware": {
      "mcpTools": {
        "get_anything": { "allow": { "enabled": true } },
        "get_users": { "allow": { "enabled": true } },
        "get_products": { "allow": { "enabled": true } }
      }
    }
  }
}
curl -s http://localhost:8080/tyk/mcps \
  -H "x-tyk-authorization: $APISecret" -H "Content-Type: application/json" \
  -d @mcp-proxy.json
⚠ Verified — the single most important finding in this whole guide. That's POST /tyk/mcps, not /tyk/apis/oas. Registering through the generic OAS endpoint creates a perfectly working reverse proxy — MCP traffic flows fine either way — but it never sets ApplicationProtocol="mcp", and the gateway's IsMCP() check staying false silently disables both the tool-allowlist and per-tool rate limiting (found by reading the gateway's own Go source). Nothing errors — the governance features just never engage. /tyk/mcps is the dedicated endpoint that actually turns them on. setup.sh already uses the correct one.

setup.sh already registered this and created a demo key for you (/tmp/tyk_mcp_key.txt). Show one authenticated tools/list call succeeding through localhost:8080/mcp-gw/mcp, and one unauthenticated call to the same path failing — the whole pitch, in two curl commands.

Verified, a real gotcha: tyk-mock-mcp-server registers its handler at the exact path /mcp (no trailing slash, exact match, no subtree routing). If your listenPath is also /mcp/ and clients call .../mcp/, the stripped remainder is empty and every call 404s from the upstream server (a plain-text 404, not Tyk's JSON error shape — that's the tell). Use a different listenPath prefix (/mcp-gw/) so the client's URL (.../mcp-gw/mcp) leaves mcp as the stripped remainder Tyk forwards upstream. Already fixed in this repo's tyk/mcp-proxy.json.

Segment 4 — run the agent, then break it on purpose

Install and configure

python3 --version   # needs 3.10+ — agent.py uses `dict | None` (PEP 604) syntax
python3 -m venv .venv && source .venv/bin/activate   # sidesteps macOS's "externally-managed-environment" pip error
pip install -r requirements.txt
export TYK_MCP_URL="http://localhost:8080/mcp-gw/mcp"
export TYK_MCP_KEY="$(cat /tmp/tyk_mcp_key.txt)"   # written by ./setup.sh
Verified, two real onboarding gotchas: macOS's built-in python3 is often older than 3.10 — check the version before assuming a pip install failure is something else. And Homebrew's Python refuses a bare pip install with "externally-managed-environment" (PEP 668) — a venv (above) is the clean fix.

agent.py genuinely supports two modes now (this used to be a documentation claim that didn't match the code — fixed): with all three AI_STUDIO_* vars set, it runs the full LLM+tools loop; with any missing, it discovers tools and calls one directly with no LLM in the loop, so the tool-governance path still demos cleanly even with segment 3's AI Studio caveat in play. If you do have the completions call working:

export AI_STUDIO_BASE_URL="http://localhost:9091/llm/call/workshop-llm/v1"
export AI_STUDIO_API_KEY="$(cat /tmp/ai_studio_key.txt)"   # written by ai-studio/setup.sh
export AI_STUDIO_MODEL="claude-3-5-haiku-20241022"   # bare model name — the slug is already in the base URL

Run it

python agent.py "How many users are in the system, and who is user 1?"

Walk through what happens on screen: the model decides it needs a tool, the script calls tools/call against the Tyk MCP Gateway (not the raw MCP server), gets a result, and the model uses it to answer. Point at the terminal, not the slide, for this part.

Verified: the streamable-HTTP MCP transport requires a real session handshake first (initialize → capture Mcp-Session-Id → notifications/initialized → then tools/call works). A bare tools/call with no handshake returns 200 with an "invalid during session initialization" error. agent.py's McpSession class does this for you now.

Governance beat #1 — filtered discovery

Create a second key scoped to fewer tools (or none). Re-run tools/list with it and show the tool list is shorter — the agent literally cannot see tools it isn't authorized for.

Verified, a real nuance: the tool allowlist is scoped to the API definition, not the key — every key on mock-mcp-governed sees the same allowed set. Calling a disallowed tool is genuinely denied (a real 403, confirmed live), but narrowing what one specific key can see in tools/list needs a second, more-restrictive MCP proxy API definition, with the narrower key's access_rights pointing at that instead. A few minutes of prep, not a code change.

Governance beat #2 — trip the rate limit

# Real MCP session handshake first — capture Mcp-Session-Id from initialize,
# then send it on every later call.
SID=$(curl -s -D - http://localhost:8080/mcp-gw/mcp \
  -H "Authorization: Bearer $TYK_MCP_KEY" -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"demo","version":"1.0"}}}' \
  -o /dev/null | grep -i Mcp-Session-Id | tr -d '\r' | awk '{print $2}')
curl -s http://localhost:8080/mcp-gw/mcp -H "Authorization: Bearer $TYK_MCP_KEY" \
  -H "Content-Type: application/json" -H "Accept: application/json, text/event-stream" -H "Mcp-Session-Id: $SID" \
  -d '{"jsonrpc":"2.0","method":"notifications/initialized"}' >/dev/null

for i in $(seq 1 8); do
  curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080/mcp-gw/mcp \
    -H "Authorization: Bearer $TYK_MCP_KEY" \
    -H "Content-Type: application/json" -H "Accept: application/json, text/event-stream" -H "Mcp-Session-Id: $SID" \
    -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"get_anything","arguments":{}}}'
done

TYK_MCP_KEY fresh off setup.sh has no rate limit yet — this loop is a deliberate "happy path" that returns eight 200s. Apply a 5/min limit on get_anything live with a PUT /tyk/keys/{key} (exact command in CHEATSHEET.md §1b), re-run the same loop, and requests 6–8 come back 429: confirmed live, five 200s then three 429s, exactly as expected. Then remove it again (§1c) and show it's back to all 200. Point out the live Tyk logs showing the calling key's identity attached to the "Rate Limit Exceeded" line: that's the audit trail, for free, from infrastructure the agent code never had to implement.

⚠ Verified — the fix that made both beats above work at all. Neither enforced anything the first time this was tried. The cause, found by reading the gateway's own Go source: mock-mcp-governed must be registered via POST /tyk/mcps, not /tyk/apis/oas (see segment 2) — only that endpoint sets ApplicationProtocol="mcp", which turns on both the allowlist and rate-limit enforcement. Separately, the rate limit itself lives on the key (access_rights.<api_id>.mcp_primitives), not the API definition.
Also verified: setup.sh creates TYK_MCP_KEY with a fixed, custom key ID (POST /tyk/keys/{custom-id} instead of the default POST /tyk/keys/create), so the resulting key value is deterministic — re-running setup.sh always reproduces byte-for-byte the same key. This closes a real bug found while testing: the default random-key behavior means exporting the key once, then re-running setup.sh later, silently leaves your shell holding a dead value.

Governance beat #3 — the cost/usage view

Flip back to the AI Studio UI and show the usage/cost panel ticking up as agent.py made its model calls. Say explicitly which parts are CE (the tracking you're looking at) vs. Enterprise (budget alerts/enforcement, full audit-log persistence, SSO) so you don't overclaim live.

07 · Live, ~15 min

Part 2 — identity governance: OAuth 2.0 token exchange, on Tyk OSS only

Runs in part2-token-exchange/, on the same kind cluster and Tyk OSS Gateway as segments 2–4 — an additional governance pillar layered on top, not a separate stack. Where segments 2–4 showed "auth, rate limits, tool allowlisting" and "LLM cost/RBAC," this shows a third: identity delegation — an agent acting on behalf of a specific signed-in human, its access narrowed to exactly the one action it's performing, while the human's identity is preserved end to end.

Why this needed its own approach

The scenario (Acme Support Copilot) comes from Tyk's tyk-demo repo's mcp-token-exchange deployment, which demonstrates RFC 8693 OAuth Token Exchange using Tyk's built-in Enterprise middleware — a hard licence requirement, confirmed by that deployment's own pre.sh, and a silent no-op on the OSS gateway.

To keep this workshop genuinely all-OSS, this reimplements the same observable behaviour — narrow an inbound token's scope to one action while preserving identity — using Tyk's gRPC "rich plugin" system, which has shipped in the Community Edition gateway for years, independent of and predating the Enterprise MCP-exchange bundle. A small Python gRPC service reads the already-JWT-authenticated request, checks the caller's entitlements claim against the one scope the requested tool needs, and either denies with 403 or mints a fresh, short-lived, self-signed JWT that keeps sub but re-points aud/scope.

Verified end-to-end against a live kind cluster — real Keycloak login, real Tyk OSS Gateway, real gRPC plugin, real narrowed-token verification at a second Tyk-fronted API.

Sign out, sign in as bob (read+refund), and the refund succeeds. The Delegation inspector shows both tokens: same sub, narrower scope, aud re-pointed to api.acme.internal, azp = tyk-mcp-gateway.

Prefer a headless check? ./verify.sh (with the gateway and Keycloak port-forwards running) drives the same three scenarios and prints PASS/FAIL — the exact script used to confirm this works before this guide was written.

The one landmine worth knowing about before you improvise on stage

If you write your own Tyk policy file for a JWT-auth API's defaultPolicies: the tyk-helm/tyk-oss chart sets both Policies.PolicyPath (a directory) and Policies.PolicyRecordName (a file). Tyk prefers PolicyPath when set, which decodes every file in that directory as one single policy object per file — not the map-of-named-policies shape most classic examples show. Get this wrong and there's no error: the gateway logs "Policies found (N total)" happily, and every request then fails with policy not found, because the file decoded into an empty struct. Already handled in both setup.sh scripts.

11 · Closing line

"Why not just build this into the agent?"

Because then every team building an agent reimplements auth, rate limiting, and audit logging themselves, inconsistently, and usually skips the audit logging. Putting it in a gateway means the policy is centrally owned, applies uniformly across every agent and every MCP server in the org, and shows up in the same dashboards your platform team already watches for REST traffic. That's the whole argument, and it's the one to end on.
